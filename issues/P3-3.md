# P3-3 — `register()` installs process-global handlers with no unregister path; …

## Finding / 问题

- EN: `register()` installs process-global handlers with no unregister path; the test class restores them by re-registering, so DebugPage's handlers remain installed after the suite runs. Harmless today, fragile later.
- 中文: register() 装的是进程级全局处理器且无卸载路径；测试类只是重新注册以「恢复」，跑完后 DebugPage 的处理器仍挂着。当前无影响，后续脆弱。
- Where / 位置: `src/DebugPage.php:39-63; tests/DebugPageTest.php:147-153`
- Verification / 验证: static / 仅静态推断

- 2026-09-29 · `owner — migears-debug` · `question` — the item has two clauses and they land differently; the
  first is fixed, the second forks on a decision the user owns.
  - Clause "the test class restores them by re-registering" has changed: `tests/DebugPageTest.php:145-179` now use
    `restore_exception_handler()` / `restore_error_handler()`. The *effect* the finding names is still real, and I
    reproduced it (PHP 8.5.10): mirroring the three register tests left a live handler of each kind. Each test
    cleaned only the kind it asserted, so T1/T2 leaked the error handler and T3 leaked the exception handler;
    `set_exception_handler(fn () => null)` and `set_error_handler(fn () => null)` each returned a `DebugPage`
    closure afterwards.
  - Fixed that leak in this pass, no code or API change: every register test now unwinds both kinds it installed
    (`tests/DebugPageTest.php:150-152`, `:162-164`, `:174-176`), and a guard
    `tests/DebugPageTest.php:181 testRegisterHandlersAreUnwoundAfterRegisterTests` detects a leftover by inspecting
    the handler closure's captured `DebugPage` instance (`tests/DebugPageTest.php:451`). Fail-without-fix proof
    (mutation): reverting only the three cleanup lines and running `./vendor/bin/phpunit --filter Register` exits 1
    with `Failed asserting that MiGears\Debug\DebugPage Object … is null`; restored, the full suite is green.
  - What is NOT fixed, because it forks on a decision the user owns — giving `register()` a first-class
    **unregister path**. That is a public-API addition, and the shutdown callback PHP stores cannot be removed at
    all (`register_shutdown_function()` has no counterpart), so no code change makes registration fully
    reversible. Options and costs:
    1. add `public static function unregister(): void` — restores one exception + one error handler; new public
       surface to document and test, and still only partially reversible because the shutdown callback stays
       (cost: more API on a dev-only bootstrap helper);
    2. leave the API as-is and rely on the fixed tests plus the documented "register once at bootstrap" intent
       (cost: none in code; a future caller still cannot unregister);
    3. inject the handlers behind a seam (e.g. a registry object) — cleanly reversible, but a design change well
       past this P3 and against the module's one-class, zero-dependency shape (cost: the most).
    I recommend option 2 and am not touching the public surface pending the decision.
